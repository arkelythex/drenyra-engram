# Spec — v1-readiness

> Phase: spec · Artifact: spec · Status: draft
> Inputs: proposal (required). Strict TDD: not active in this phase.
> Store: OpenSpec file-based (openspec/changes/v1-readiness/spec.md). No engram writes.

## Scope

This change makes the existing trust model demonstrable for the v1 gate by adding three additive, read-only evidence surfaces plus the operational documentation that proves them: **(G-6)** Go fuzz targets for the three highest-risk parser/decoder areas, a read-only SQLite health-check surface on the existing `doctor` report, a corruption drill that operates only on disposable database copies, a restore drill with mandatory verify-after-restore, and bounded (30s) CI fuzzing; **(G-7)** a key-compromise response playbook aligned to NIST SP 800-57, a gap analysis of `SigningKeyForVerify`/`revoked_at`, and frozen, tested cutoff semantics — reject signatures issued at or after the authenticated compromise timestamp, retain pre-cutoff signatures under explicit policy; **(G-10)** a read-only `reconstructibility` surface for one exact company scope + period whose denominator (material decisions), numerator (reconstructible decisions), reason categories, and zero-denominator representation are frozen in this spec before any implementation. No product UI, no new authority, no breaking contract change: every surface is an observation, money stays whole `int64`/`BigInt` cents, and any new shared pure logic joins the `testdata/golden` Go↔TS parity mechanism.

## Requirements

### Frozen definitions (binding — design and apply MUST NOT deviate)

The following four definitions are the open questions the proposal left for the spec. They are frozen exactly as written here; any later change requires a new proposal + spec amendment.

- `FZ-1` — **G-10 material-decision eligibility (denominator).** A memory is a **material decision** in the queried scope/period if and only if ALL of the following hold:
  1. it is the LATEST revision of its `topicKey` chain (superseded/voided/rejected/returned/draft/pending revisions never count);
  2. its `Scope` is an exact company scope (`ScopeKindCompany`) whose `CompanyID`/`RUC` equal the queried company AND its `Scope.Period` equals the queried period byte-for-byte;
  3. its `Status` is exactly `StatusApproved` (the human-approval gate; `active`, `pending_review`, `returned`, `rejected`, `voided`, `superseded` are excluded — this is the baseline-stability rule);
  4. its `FiscalEffect` is one of exactly: `FiscalEffectJournalEntry`, `FiscalEffectAdjustment`, `FiscalEffectReclassification`, `FiscalEffectDeclaration`, `FiscalEffectClosing`, `FiscalEffectSunatFiling` (`FiscalEffectNone` and `FiscalEffectApproval` are NOT eligible);
  5. its declared `MaterialityLevel` is `MaterialityMaterial` or `MaterialityCritical` (nil/NULL — which means `normal` — is NOT eligible).
  The numeric `Materiality` cents threshold field MUST NOT participate in eligibility (frozen decision: the write-time-validated level enum is the only eligibility signal, keeping the denominator deterministic and cross-revision stable).
- `FZ-2` — **G-10 reconstructibility.** A material decision counts in the numerator if and only if ALL of the following hold, evaluated in this frozen order with the FIRST failure assigning the decision's single bounded reason category:
  1. **(a) approval** — the decision's current status is `StatusApproved`; failure reason `not_approved`. In v1 this is structurally unreachable for denominator members because `FZ-1` already requires `approved`; the category is still a frozen member of the closed vocabulary, unit-tested at the classifier level, and protects the metric contract if eligibility ever evolves.
  2. **(d) receipt** — the decision's full signed receipt chain passes every receipt layer (payload canonicalization, envelope integrity, signature, signing-key validity, tenant/company scope, chain link) AND the principal-provenance layer passes for the `memory_approved` approval receipt; failure reason `receipt_failed`.
  3. **(b) evidence** — the evidence-availability layer (`LayerEvidenceAvailability`) passes; failure reason `missing_evidence`. Then the object-availability layer (every resolved evidence object's WORM bytes re-hash to its content address) must pass; failure reason `evidence_missing_object`.
  4. **(c) rule** — the rule-availability layer (`LayerRuleAvailability`) passes; failure reason `rule_unresolved`. Then the rule-version/vigencia layer (`LayerRuleVersionVigencia`) must pass, i.e. every structured rule trace outcome is `RuleVersionResolved` or `RuleVersionLegacySkipped`; failure reason `rule_version_failed`.
  The complete, closed reason vocabulary is exactly: `not_approved`, `receipt_failed`, `missing_evidence`, `evidence_missing_object`, `rule_unresolved`, `rule_version_failed`. A decision is never classified with more than one reason, and no other reason string may be emitted.
- `FZ-3` — **G-7 cutoff semantics.** Verification MUST reject a signature when the signing key is revoked AND `issued_at >= revoked_at`; the equal-timestamp case is REJECTED (deterministic: equality fails). Verification MUST accept a signature when `issued_at < revoked_at` and every other layer passes — pre-compromise artifacts are retained as valid under the explicit policy recorded in the playbook (NIST SP 800-57: pre-compromise artifacts may be retained under explicit policy). Verification MUST also reject when `created_at > issued_at`. Both timestamps MUST parse as RFC3339; a revoked key whose `revoked_at` cannot be parsed is a fail-closed error, never a guess. A revoked key MUST never sign new receipts.
- `FZ-4` — **G-6 drill and fuzz surfaces.** The SQLite health-check surface extends the existing `DoctorReport` with `quickCheck`, `integrityCheck`, `foreignKeyCheck`, and `cellSizeCheck` results (routine doctor = `quick_check` + `foreign_key_check`; full `integrity_check` runs only on the explicit drill/diagnostic path and is always paired with `foreign_key_check`). The corruption drill operates ONLY on a disposable, consistently snapshotted COPY of a database — never the live DB and never a blind copy of a live WAL DB. The restore drill uses `VACUUM INTO`, the SQLite backup API, or an equivalent WAL-safe snapshot, produces a separate output, and MUST NOT release the restored DB for use until integrity, foreign-key, scope-conformance, and expected backup-identity checks all pass. Fuzz targets are exactly the three named in `FR-1` with the invariants, seed policy, and CI bound stated there.

### Functional requirements

- `FR-1` — **G-6 fuzz targets (exactly three).** As a maintainer I want deterministic, bounded fuzzing of the highest-risk parser/decoder surfaces so that malformed inputs produce typed results or regressions, never crashes or silent invalid success. The three frozen targets are:
  - `FuzzParseComprobanteXML` in `internal/core` — drives `ParseComprobanteXML` and `ParseCDRXML` (`internal/core/comprobante.go`).
  - `FuzzCanonicalReceiptPayload` in `internal/core` — drives `CanonicalReceiptPayload`, `CompleteReceiptBytes`, and `ReceiptHash` (`internal/core/receipt.go`) across the frozen payload versions (`receipt-payload/v0.4.0` … `v0.10.0`).
  - `FuzzSearchTokenize` in `internal/search` — drives `tokenize` (`internal/search/search.go`).
  Every target MUST enforce all of: (i) no panic on any input; (ii) deterministic output — identical input always yields identical output bytes; (iii) round-trip stability where defined — canonical receipt payloads must re-parse and re-canonicalize to byte-identical output; (iv) no invalid successful result — a nil error must yield a result that satisfies the target's frozen validity contract (parsed `Comprobante` fields conform to the schema; emitted tokens are non-empty and contain no separator characters; canonical payload bytes re-parse to a payload that re-canonicalizes identically); (v) bounded per-input size — every target MUST ignore inputs larger than 1 MiB (documented in the target doc comment), so expensive non-crashing inputs stay bounded without weakening the parsers.
- `FR-2` — **G-6 seed corpus and crasher policy.** As a maintainer I want a committed seed corpus per target so CI fuzzing starts from valid, boundary, malformed, and previously-failing inputs and every found crasher becomes a permanent regression. Each target MUST have seeds committed under `testdata/fuzz/<FuzzTargetName>/` covering: valid production-shaped samples, boundary samples (empty input, 1 byte, maximum size, size just below the cap), malformed samples (truncated XML, wrong encoding, nested/unbounded depth probes, invalid UTF-8 for the tokenizer, canonical-shape violations for receipts), and every previously-failing input. A crasher found by any fuzz run MUST be minimized, committed under the same directory, and MUST remain green under `go test ./...` (Go runs committed corpus files as unit tests); crashers MUST NOT be deleted while the underlying bug class exists, and fixes MUST add a named unit regression test where the corpus file alone does not document the fix.
- `FR-3` — **G-6 bounded CI fuzzing.** As a maintainer I want a bounded CI fuzz gate so regressions in the three targets are caught without unbounded CI time. The repository MUST provide a `make fuzz-ci` target (or an equivalent CI job) that runs each of the three targets with `-fuzztime=30s` (e.g. `go test ./internal/core -run '^$' -fuzz=FuzzParseComprobanteXML -fuzztime=30s` and the equivalent invocations for the other two targets). Unbounded fuzzing remains an operator-local option and MUST NEVER be a CI gate. The `fuzz-ci` target MUST NOT weaken any parser invariant to stay within budget.
- `FR-4` — **G-6 SQLite health-check surface.** As an operator I want the existing `doctor` surface to report SQLite structural health so corruption is detected before data becomes unrecoverable. The `store.DoctorReport` MUST be extended with: `quickCheck` (status ok/failed + detail) — the routine doctor path MUST always run `PRAGMA quick_check`; `integrityCheck` (status ok/failed + detail) — MUST run `PRAGMA integrity_check` ONLY on the explicit drill/diagnostic path, never on routine doctor; `foreignKeyCheck` (status ok/failed + violation count + detail) — MUST be run and reported alongside every integrity check (routine and full); `cellSizeCheck` (effective state on/off) — `cell_size_check=ON` MUST be enabled where compatible with the existing connection lifecycle and MUST otherwise be documented; the report MUST always state its effective value so the evidence is inspectable. All checks are read-only observations and MUST NOT mutate the database.
- `FR-5` — **G-6 corruption drill (copy-only, fail closed).** As an operator I want a repeatable drill that proves the engine detects deliberate corruption, freezes writes, preserves evidence, and never repairs in place. The drill MUST: (i) operate on a disposable copy created from a consistent (WAL-checkpointed) snapshot — never the live database and never a blind copy of a live WAL database; (ii) deliberately damage the copy (e.g. page-level byte corruption) in a deterministic way; (iii) detect the damage through the `FR-4` check surface; (iv) after detection, cause the affected database to fail closed — subsequent writes MUST be refused with a typed error and MUST NOT silently continue; (v) preserve the corrupted copy byte-for-byte as evidence at a designated path; (vi) never attempt in-place repair. Reopening writes MUST require the explicit operator-issued verified-restore path of `FR-6`; the engine MUST NOT auto-reopen and MUST NOT itself authorize recovery (non-authorization boundary).
- `FR-6` — **G-6 restore drill (verify-after-restore).** As an operator I want a restore drill that proves a WAL-safe snapshot can be restored and verified before use. The drill MUST: (i) create a WAL-safe snapshot via `VACUUM INTO`, the SQLite backup API, or an equivalent mechanism; (ii) restore it to a separate output (source and output never shared); (iii) run verify-after-restore before the restored database may be used, in this order — integrity check, `foreign_key_check`, scope-conformance check (the expected company/RUC/period rows are present and consistent), and expected backup-identity check (restored bytes/metadata match the source snapshot identity); (iv) reject the restore with a typed error if ANY check fails — a readable database alone is insufficient; (v) leave the source snapshot untouched. The restored output may only enter use after all four checks pass.
- `FR-7` — **G-7 gap analysis and playbook.** As an operator I want a documented, NIST-aligned key-compromise response so a known compromise has a deterministic sequence and the engine's cutoff behavior is confirmed against the frozen contract. This change MUST add `docs/security/key-compromise-response.md` with the eight-step operator sequence from the proposal (treat exposure as full trust failure; stop signing and suspend verification with the compromised key; preserve evidence and record the exact compromise time; generate an independent replacement keypair in a clean environment; publish an authenticated revocation; fail closed for signatures issued at or after the cutoff; inventory and re-sign affected artifacts where policy permits; investigate adjacent systems). The change MUST also record a gap analysis of `SigningKeyForVerify`/`LookupSigningKey` and the current `revoked_at` semantics (read-only verification path, one-way revoke-only trigger, no transaction on the verification surface) compared against `contracts/verification.md`. The gap analysis MUST conclude either (a) implementation matches the frozen contract — evidence quoted in the playbook — or (b) a mismatch, in which case verification MUST be hardened within this change so implementation and contract agree on `FZ-3`.
- `FR-8` — **G-7 cutoff boundary enforcement.** As a verifier I want the signing-key-validity layer to reject signatures at or after an authenticated compromise cutoff and accept demonstrably pre-cutoff signatures, with the exact `FZ-3` comparison. The verification layer MUST reject when the key is revoked and `issued_at >= revoked_at`; MUST accept when `issued_at < revoked_at` (all other layers passing); MUST reject when `created_at > issued_at`; MUST reject when a revoked key's timestamps do not parse as RFC3339 (fail closed, no guessing). Missing or unauthenticated cutoff information MUST NOT be accepted as a cutoff (only the authenticated one-way `signing_keys.revoked_at` update is a cutoff). A revoked key MUST NOT sign new receipts. No contract file changes are required by this requirement — `contracts/verification.md` already freezes this layer; `FR-7`'s gap analysis must prove implementation == contract, and the focused boundary tests in `AC-8` become permanent regressions.
- `FR-9` — **G-10 read-only reconstructibility surface.** As an operator I want a deterministic, read-only baseline of material decisions reconstructible to evidence + rule + approval for ONE exact company scope and period, repeatable without mutating accounting state. The surface MUST: (i) take exactly one company scope (exact `CompanyID`/`RUC`) and one period, and FAIL CLOSED with a typed error when scope or period is missing, ambiguous, or mismatched — cross-tenant aggregation is forbidden; (ii) compute the denominator with `FZ-1`, the numerator with `FZ-2`, and report, per `FZ-2`'s frozen order and vocabulary, the per-category non-reconstructible decision IDs ordered deterministically by decision ID; (iii) return the frozen result shape: `{scope, period, denominator, numerator, ratio: {numerator, denominator}, percentage, reasons: {not_approved, receipt_failed, missing_evidence, evidence_missing_object, rule_unresolved, rule_version_failed}, zeroDenominator}` where `percentage` is integer division `(numerator * 100) / denominator` computed in integer math (never floating point) and is `null` when `denominator == 0`; (iv) represent the empty period explicitly — `denominator == 0`, `numerator == 0`, `ratio {0, 0}`, `percentage null`, `zeroDenominator true` — NEVER a misleading 0% or 100%; (v) be read-only: computing the baseline MUST NOT mutate decisions, approvals, evidence, receipts, or lifecycle state, and MUST run over read-only paths (the same no-transaction discipline as `SigningKeyForVerify`); (vi) be deterministic: two runs against the same store snapshot MUST return byte-identical results (frozen field order, sorted reason-ID lists). The surface MUST reuse the existing verification and rule-version tracing machinery — it MUST NOT build a second reconstruction truth model.
- `FR-10` — **G-10 exposure boundary.** As a consumer I want the baseline reachable through existing adapter conventions without inventing new authority. The canonical service/result model MUST live in `internal/server` and MUST be exposed at minimum via the CLI following the existing `doctor` command pattern (JSON report on stdout). HTTP/MCP exposure MAY be added only where an existing read-only diagnostic adapter pattern already exists (e.g. the `engram_doctor` MCP tool pattern); no new adapter kind may be introduced by this change. All exposures remain observations and MUST NOT authorize, post, file, or approve anything.

### Non-functional requirements

- `NFR-1` — **Performance (metric):** the reconstructibility metric MUST be read-only and deterministic (`FR-9` vi); all data access MUST be scoped to the exact company + period by SQL/structural scope (never a post-filter); the surface MUST NOT scan beyond the queried scope; full `integrity_check` MUST NOT run on routine paths (`FR-4`); CI fuzzing MUST be bounded to `-fuzztime=30s` per target (`FR-3`).
- `NFR-2` — **Security:** no new authority — health, verification, and reconstructibility results are observations and MUST NOT grant, suspend, or imply authorization; the corruption write-freeze MUST fail closed and MUST NOT be bypassable by a retry; a revoked signing key MUST NOT sign and MUST NOT verify at/after the cutoff (`FZ-3`); fuzz seeds, corruption fixtures, and drill artifacts MUST contain no credentials, tokens, or customer data (config `secrets` convention).
- `NFR-3` — **Parity:** any new shared domain result or pure logic with cross-runtime consumers — at minimum the eligibility predicate (`FZ-1`), the reconstructibility classifier (`FZ-2`), and the ratio/percentage computation (`FR-9` iii) if exposed as a shared contract — MUST join the `testdata/golden` Go↔TS byte-identical vector mechanism enforced by `TestGoldenVectorsGo`. Go-only operational drill controls (doctor checks, corruption/restore drills) need not be mirrored unless they expose a shared contract.
- `NFR-4` — **Determinism and auditability:** every drill MUST leave byte-preserved evidence; restore MUST be rejected until all four verify-after-restore checks pass (`FR-6`); the playbook MUST record the exact compromise time and preserve the security event trail; the metric MUST be repeatable with identical output on an unchanged snapshot.
- `NFR-5` — **Compatibility:** no breaking public-contract change. If the gap analysis (`FR-7`) discovers a required contract change, it MUST follow the frozen-contracts rule: version bump, migration path, and explicit approval — and it MUST NOT be silently shipped.

### Invariant requirements (Drenyra Engram standing rules)

- `IR-1` — Money remains whole int64 cents / BigInt cents; no float path is introduced (the metric's percentage is integer division; money never appears in drill or metric arithmetic).
- `IR-2` — Scope stays structural and fails closed on mismatch (the metric and drills take exact scope and refuse ambiguity).
- `IR-3` — Non-authorization boundary holds: no new surface approves, posts, files, or reopens writes on its own.
- `IR-4` — Go↔TS golden parity is extended for new shared domain logic (`FZ-1`/`FZ-2`/ratio), enforced via `testdata/golden` and `TestGoldenVectorsGo`.
- `IR-5` — No `any` in TypeScript; precise types or `unknown`.

## Acceptance criteria

- `AC-1` — Three fuzz targets exist (`FuzzParseComprobanteXML`, `FuzzCanonicalReceiptPayload`, `FuzzSearchTokenize`) in the frozen packages with the frozen invariants; `go test ./...` runs each target's committed corpus green; each target documents its 1 MiB input cap.
- `AC-2` — `make fuzz-ci` (or equivalent CI job) runs all three targets with `-fuzztime=30s` and exits non-zero on any failure; CI never runs unbounded fuzzing; a seeded crasher committed under `testdata/fuzz/` triggers a red `go test` when reintroduced and is fixed, not deleted.
- `AC-3` — `doctor --db <db>` reports `quickCheck`, `integrityCheck` (drill path only), `foreignKeyCheck`, and `cellSizeCheck` in `store.DoctorReport`; routine doctor runs `quick_check` + `foreign_key_check` and never `integrity_check`; full `integrity_check` is reachable only via the explicit drill/diagnostic path and is paired with `foreign_key_check` (test asserts the pairing).
- `AC-4` — A corruption drill test: a disposable copy of a consistent DB is corrupted → the check surface detects it → subsequent writes are refused with the typed error → the corrupted copy is preserved byte-for-byte as evidence → no in-place repair is attempted → the live DB is untouched.
- `AC-5` — A restore drill test: a WAL-safe snapshot is restored to a separate output → verify-after-restore (integrity, foreign key, scope conformance, backup identity) passes → the restored DB is usable; a deliberately broken restore (corrupted output, wrong identity, missing scope rows) is rejected with a typed error and never released for use.
- `AC-6` — `docs/security/key-compromise-response.md` exists with the eight NIST-aligned steps and a recorded gap analysis of `SigningKeyForVerify`/`revoked_at` concluding either implementation==contract with quoted evidence or a hardening item implemented in this change.
- `AC-7` — Cutoff enforcement tests pin the exact `FZ-3` comparison and are green: `issuedAt < revokedAt` → valid (all other layers passing); `issuedAt == revokedAt` → rejected; `issuedAt > revokedAt` → rejected; `createdAt > issuedAt` → rejected; revoked key refuses to sign; revoked key with unparseable `revoked_at` fails closed; a revoked-but-never-cutoff (empty `revoked_at`) key behaves per the current contract.
- `AC-8` — Metric determinism tests: the eligibility matrix (`FZ-1`) and classifier precedence (`FZ-2`) are unit-tested over synthetic memories covering every enum member and every reason category, including a direct `not_approved` classifier case; two runs against the same snapshot return byte-identical JSON; cross-tenant probes return zero results and scope mismatch fails closed; a zero-denominator scope returns `denominator 0`, `numerator 0`, `ratio {0,0}`, `percentage null`, `zeroDenominator true` — never 0% or 100%; computing the baseline leaves a pre-computed store-state hash unchanged (read-only proof).
- `AC-9` — New shared pure logic (`FZ-1`, `FZ-2`, ratio/percentage) has Go↔TS golden vectors under `testdata/golden` and `go test ./internal/core -run TestGoldenVectorsGo` is green; drill-only Go controls are not mirrored unless they expose a shared contract.
- `AC-10` — No `any` introduced in TypeScript; no float path for money or percentage; no new authorization surface (reviewer check: every new CLI/MCP/HTTP surface is read-only and observational).
- `AC-11` — `go test ./...` and `npm test` remain green; `npm run typecheck` clean; `go vet ./...` and `gofmt -l .` clean.

## Out of scope

- No product UI.
- No production SUNAT or ERP integration.
- No identity-provider, MFA, or membership implementation.
- No external or third-party security review.
- No authorization, filing, payment, declaration, or execution capability; the engine never reopens writes on its own and never authorizes recovery.
- No claim that cryptographic integrity proves accounting correctness.
- No destructive corruption of a live database and no blind copy of a live WAL database.
- No pricing metric or customer-observed North Star target (G-10 closes its engineering baseline only; the customer-observed target remains open).
- No breaking contract change. Any contract change found necessary by the gap analysis requires a version bump, migration path, and explicit approval under `openspec/config.yaml`.
- No new adapter kind for the metric beyond existing read-only diagnostic patterns.

## Test plan

Obsessive by design — every acceptance criterion has at least one automated proof, and the failure paths are tested as first-class citizens:

- **Fuzz (AC-1, AC-2):** `internal/core` fuzz tests for `FuzzParseComprobanteXML` (targeting `ParseComprobanteXML` + `ParseCDRXML`) and `FuzzCanonicalReceiptPayload` (targeting `CanonicalReceiptPayload`/`CompleteReceiptBytes`/`ReceiptHash` over payload versions `v0.4.0`–`v0.10.0`); `internal/search` fuzz test for `FuzzSearchTokenize` (targeting `tokenize`). Each target asserts no-panic, determinism, round-trip stability, no-invalid-success, and a 1 MiB input cap. Seed corpora committed under `testdata/fuzz/<Target>/` with valid/boundary/malformed/previously-failing inputs; minimized crashers committed and green under `go test ./...`; `make fuzz-ci` runs `-fuzztime=30s` per target. A regression test proves a known crasher turns CI red before its fix and stays green after (fix never deletes the corpus entry).
- **Health checks (AC-3):** `internal/store` tests assert `quick_check` + `foreign_key_check` on routine doctor, `integrity_check` only on the explicit drill path, the mandatory pairing of `integrity_check` with `foreign_key_check`, and `cellSizeCheck` reporting the effective `cell_size_check` state; CLI test extends the existing `doctor` JSON contract test (`cmd/drenyra-engram/main_test.go` doctor block) for the four new fields.
- **Corruption drill (AC-4):** a test builds a consistent DB, copies it (WAL-checkpointed), deterministically flips page bytes in the copy, runs the check surface, asserts detection, asserts the next write returns the typed fail-closed error, asserts the corrupted copy is byte-identical before/after detection (evidence preserved), asserts no repair write occurs, and asserts the live DB is untouched.
- **Restore drill (AC-5):** a test snapshots via `VACUUM INTO`/backup API, restores to a separate output, runs verify-after-restore in order (integrity → foreign key → scope conformance → backup identity), asserts success path usability; negative tests: corrupted restored output, wrong backup identity, and missing scope rows each produce a typed rejection and the output is never released.
- **Cutoff boundary (AC-7):** table-driven tests over before/at/after the cutoff with RFC3339 timestamps (equal-timestamp case pinned to rejection), `created_at > issued_at`, revoked-key-cannot-sign, unparseable `revoked_at` fail-closed, and empty-`revoked_at` behavior; each case runs against the pure `VerifySigningKeyValidity` layer (internal/core unit) and through the verification service path (`internal/server` integration) where a receipt chain exists.
- **Metric (AC-8):** pure unit tests for the eligibility predicate (every `FiscalEffect` member, every `MaterialityLevel` member incl. nil, every status, latest-revision-only, exact scope/period matching, cross-period exclusion) and the classifier precedence (each of the six reason categories reachable in the unit surface, incl. a direct `not_approved` case); integration tests against a seeded store: correct denominator/numerator/ratio/percentage; zero-denominator representation; cross-tenant probe isolation; scope-mismatch fail-closed; byte-identical double-run determinism; read-only proof via store-state hash before/after.
- **Golden parity (AC-9):** new shared pure logic (`FZ-1`, `FZ-2`, ratio/percentage) joins `testdata/golden` Go↔TS vectors; `go test ./internal/core -run TestGoldenVectorsGo` green; TS mirrors updated in the same change.
- **Scope isolation conformance:** cross-tenant probes (company A data never visible from company B scope) for both the metric and the drills.
- **Full gates (AC-11):** `npm run typecheck` → `go vet ./...` → `gofmt -l .` → `go test ./...` → `npm test`, per `openspec/config.yaml` verify order.
