## Scope

Close five trust-critical audit blocks in `docs/due-diligence/2026-08-product-architecture-audit.md` from UNKNOWN/RISK to PASS with code-verifiable evidence: **L. Idempotency (186–194)**, **J. Authorization (159–175)**, **Q. Multi-tenant security (277–296)**, **Z. Operability (420–433)**, and **G. Migrations (111–122)**. The change is evidence closure, not new product capability: it adds consolidated test matrices, negative conformance tests, generated cross-tenant coverage, migration direct-upgrade/crash-recovery proof, and narrowly scoped decision documentation. No production behavior change is anticipated; any conformance test that exposes a real defect makes that criterion fail and the defect must be corrected through a separately justified, narrowly scoped change — never by weakening the matrix.

Each block section below carries its own scope boundary, requirements (`FR-<block>.<n>`), and non-functional/boundary rules (`NFR-<block>.<n>`). The frozen decisions (`FD-1`…`FD-4`) bind design and apply and MUST NOT deviate.

## Requirements

### Frozen decisions (binding — design and apply MUST NOT deviate)

These are the proposal's four open questions, accepted by default and now frozen. Any later change requires a new proposal + spec amendment.

- `FD-1` — **J: override audit is negative conformance.** Drenyra Engram has **no override feature**. Closure is a structural + behavioral negative test suite plus a frozen decision record stating that override absence is intentional and that privileged/urgent callers remain subject to the same versioned policy, scope, assurance, and SoD rules. An override feature MUST NOT be built.
- `FD-2` — **G: migration provenance is doc-only.** The ordered migration code, the one-transaction-per-step rule, and the final `schema_version` are the authoritative migration provenance record for this release. No production migration-history table, no per-deployment event ledger, and no schema v15 MAY be introduced by this change.
- `FD-3` — **Z: recovery objectives are qualitative.** No RTO/RPO (or SLA/SLO) number MAY be invented. Delivered mechanisms are documented; numerical targets remain deployment/business-owned and UNKNOWN until an owner records them.
- `FD-4` — **Q: the generated matrix is a Go test-only helper.** The cross-tenant matrix is a test-only operation catalog tied to the canonical API surface (`internal/server/api.go`). No checked-in JSON artifact and no second manually maintained API registry MAY be introduced.

### Block L — Idempotency replay and lost-response evidence (audit 186–194)

**Scope boundary (in/out):** IN — consolidated replay matrix across HTTP/MCP/CLI/sync, MCP/CLI replay cases, lost-response/interrupted-reservation cases for approval, judgment, reconciliation, review, hold, and reopen (extending the existing purge precedent), sync no-op second import, no-duplicate-effect assertions. OUT — any redesign of idempotency reservations, any change to the frozen conflict semantics, any new idempotency surface, and weakening matrix assertions to pass.

- `FR-L.1` — **Consolidated operation × surface replay matrix.** As a maintainer I want one inspectable table-driven matrix enumerating every supported idempotent operation against every applicable surface so complete replay coverage is provable in a single artifact. The matrix (proposed `TestIdempotencyReplayMatrix` in `internal/server`) MUST enumerate at least: approve memory, judgment propose/confirm/withdraw, reconciliation propose/decide/confirm/withdraw, review reject, hold place/lift, reopen period, retention-policy put, purge request/approve/reject/execute, and sync second import, each against the surfaces where it is exposed (HTTP, MCP, CLI, sync). For every (operation × surface) pair the row MUST prove: replaying the same tenant + request identifier + payload + relevant principal returns the original stored outcome with replay semantics reported where the surface exposes it (`idempotentReplay=true`), and produces no duplicate domain event, receipt, or mutation. Rows for surfaces not runnable in that test's package (CLI, sync) MUST name and link the dedicated test that proves them (see `AC-L-2`, `AC-L-3`, `AC-L-7`).
- `FR-L.2` — **Changed-input conflict.** As a caller I want reusing a request identifier with changed bound inputs to fail with the frozen typed conflict so a key can never silently produce a different outcome. For each matrix operation, reusing the request ID with a different payload or a different principal MUST fail with the frozen idempotency-conflict behavior (`IDEMPOTENCY_CONFLICT` or the per-operation typed conflict), never a silent success and never a duplicate effect. Anchors that stay green: `internal/store/approval_test.go:544 TestApproveMemoryIdempotencyConflict`, `internal/store/judgment_immutability_test.go:278 TestJudgmentConfirmIdempotencyDifferentPrincipalConflict`, `internal/store/reconciliation_test.go:736 TestProposeReconciliationConflict`, `store/__tests__/approval.test.ts:153`.
- `FR-L.3` — **MCP replay cases.** As an MCP consumer I want real replay proof on the MCP surface so the matrix is not inferred from fresh-request tests. At minimum, purge, judgment, and reconciliation MCP commands MUST have a test that replays the same request identifier and asserts the stored outcome with replay semantics (proposed `TestMCPPurgeRequestIdempotentReplay`, `TestMCPJudgmentProposeIdempotentReplay`, `TestMCPReconciliationProposeIdempotentReplay` in `internal/server`). Existing tests that only assert a fresh request is not a replay (`mcp_purge_test.go:46`, `mcp_judgment_test.go:93`, `mcp_reconciliation_test.go:74`) are NOT sufficient for this requirement.
- `FR-L.4` — **CLI replay cases.** As a CLI operator I want real replay proof on the CLI surface. Submitting the same `--request-id` twice for each idempotent CLI command (judge, reconcile, review, purge, and any other idempotent command) MUST return the stored outcome with replay semantics and no duplicate effect (proposed `TestCLIJudgeReplay`, `TestCLIReconcileReplay`, `TestCLIReviewRejectReplay`, `TestCLIPurgeRequestReplay` in `cmd/drenyra-engram`). Fresh-only assertions (`main_test.go:1137`, `judge_test.go:99`, `reconcile_test.go:109`, `review_test.go:160`, `purge_test.go:217`) are NOT sufficient.
- `FR-L.5` — **Lost-response / interrupted reservation.** As an operator I want every idempotent mutation to prove deterministic recovery when a response is lost after reservation, following the purge precedent. For approval, judgment, reconciliation, review, hold, and reopen (in addition to purge), a reservation row that was created but never completed (entity/result not stored) MUST yield a deterministic, typed outcome — replay of the original result, deterministic re-derivation per the existing reservation semantics, or the typed conflict — and MUST NOT produce a duplicate mutation, event, receipt, or a scan/decoding error. Proposals mirror `internal/store/purge_store_test.go:58 TestRequestPurgeInterruptedReservationIsConflictNotScanError` and `:121 TestRejectPurgeInterruptedReservationReplayIsConflictNotScanError`; existing purge-execution recovery anchors (`purge_execution_test.go:559`, `:713`, `:802`) stay green.
- `FR-L.6` — **No duplicate effects on replay or recovery.** As a verifier I want replay and lost-response recovery to be side-effect-free beyond the original effect. Successful replay and interrupted-reservation recovery MUST NOT create a second receipt, event, or mutation; matrix rows and recovery tests MUST assert unchanged receipt/event counts. Anchors: `internal/store/receipt_emission_test.go:429 TestApproveMemoryIdempotentRetryEmitsNoDuplicateReceipt`, `store/__tests__/receipt-emission.test.ts:305`.
- `FR-L.7` — **Sync no-op second import in the matrix.** As a sync user I want the idempotent second run represented in the consolidated evidence. The matrix MUST include sync's no-op second import (0 imports, no conflicts) even where its replay representation differs from request-ID surfaces. Anchors: `internal/sync/sync_test.go:106 TestSyncIdempotent`, `cmd/drenyra-engram/main_test.go:859 TestCLISyncRoundTrip`.

- `NFR-L.1` — **Matrix honesty.** If a matrix row exposes a real behavioral inconsistency, the criterion fails and the defect MUST be documented and corrected via a narrowly scoped, separately justified production change — never by deleting the row or widening the conflict/duplicate assertions.
- `NFR-L.2` — **Determinism and replay identity.** Replay evidence MUST bind the same tenant, request identifier, operation, payload, and relevant principal. Changed inputs under the same key are conflicts (`FR-L.2`), not successful retries.

- `NFR-XC-1` — **Strict TDD.** Apply MUST work tests-first per delivery slice (proposed slices: J, L, Q, G, Z), with each slice's tests written and failing before its implementation/fixtures land. `go test ./...` and `npm test` MUST stay green at every slice boundary; TypeScript tests MUST be run and kept green even though no shared runtime change is expected.

Any discovered shared-contract correction MUST preserve `testdata/golden` byte-identical parity (`go test ./internal/core -run TestGoldenVectorsGo`) and MUST be treated as separately approved scope (`FR`-level exception, not an incidental fix).

No percentage/ratio arithmetic in this change uses floats (integer math only, where any exists).
- `NFR-XC-4` — **Non-authorization boundary preserved.** No new surface or test helper MAY approve, post, file, reopen, or authorize anything; every new artifact is an observation or a denial assertion. - `NFR-XC-5` — **Conservative audit-register updates.** Each block flips to PASS only when ALL of its acceptance criteria with their citations have landed; no block flips on prose alone; adjacent UNKNOWN/RISK classifications (e.g. block I identity readiness, unproven production claims) are retained unchanged; a reverted/insufficient slice restores the prior status rather than leaving an unsupported PASS.

- `NFR-XC-7` — **Determinism and secrets.** All matrix and recovery tests MUST be deterministic; fixtures and docs MUST contain no credentials, tokens, or customer data (config `secrets` convention).

## Evidence contract

- `EC-1` — **PASS evidence form.** Every PASS claim in the audit register MUST cite executable evidence — a test file + `TestName` (+ line where helpful) that exercises the claim — or a frozen contract/decision document (path + section). Prose-only reconciliation is permitted ONLY for Z's stale claims and MUST pair with the executable citation of the delivered capability (`NFR-Z.1`).
- `EC-2` — **Matrix inspectability.** Matrix tests (`FR-L.1`, `FR-J.1`, `FR-Q.3`) MUST name every table row with its (operation × surface/role × expected outcome) triple so a reviewer can map each register claim to a concrete test row.
- `EC-3` — **Citation stability.** Citations MUST resolve at claim time: unique test names in the repo, or file:line anchors that exist; line numbers MAY be omitted when the test name is unique.
- `EC-4` — **Block flip rule.** A block's audit status changes to PASS only when all of that block's acceptance criteria hold with their citations in place (`NFR-XC-5`); partial evidence keeps the block at RISK/UNKNOWN with the landed evidence cited.
